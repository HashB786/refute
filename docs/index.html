The smallest input that proves your solution wrong.

Refute looks for the smallest input your program gets wrong. A language model writes the throwaway test tooling for a problem: two independent reference solutions, an input validator and an input generator.

Running the code decides, not the model. Every piece of tooling has to prove itself by running before anything it says is believed, and a failure is only reported when both reference solutions agree on the answer.

greedy.py prints 5. The right answer is 2.

From the recorded demo in this repository, which replays the model output and runs every program for real.

Install and run

git clone <this repository>
cd refute
python -m venv .venv
.venv/bin/pip install -e .
.venv/bin/refute demo

That needs no key and no network. To run it on your own solution, put a model endpoint in a .env file and use:

refute run statement.md solution.py

The demo above repeats its own finding with python examples/coin-change/greedy.py &lt; refute-out/counterexample.in.

How the model is checked

  • Two reference solutions, by different methods. Both have to reproduce every example in the statement, and a failure counts only when they agree with each other.
  • A validator that has to accept every example and reject deliberately broken copies of them: one token short, one token too many, one number out of range.
  • A generator that has to produce valid input at fifteen combinations of size and mode, give the same input for the same seed, and give different inputs for different seeds.
  • A guard that parses anything the model writes and refuses it if it imports outside a short list or reaches for open, exec, eval or dunder attributes.
  • A suggested fix is called verified only once it passes the examples, the counterexample and two hundred tests on seeds the first run never used.
  • The diagnosis is the one thing nothing can check, so it is labelled as the model's words and left unchecked.

Refute was handed each statement and each planted bug and nothing else. It never saw the reference solution that the benchmark keeps to check its own bugs with. Every bug reproduces the examples in its statement, so none of them can be caught by reading the statement. Tests to first failure and smallest input are medians over the bugs that were found; the smallest input is counted in whitespace-separated tokens.

The budget was 300 tests or 45 seconds a bug, with 15 seconds to shrink, and the tooling for a problem was written once and reused for every bug of that problem: 32 model calls for all 18 bugs.

1 bug was missed: pick-talks / by length. bench/RESULTS.md lists every bug, found or missed, with the reason it was missed.

Limits

  • No counterexample found is not the same as correct. A run that finds nothing reports how many tests it ran, how large the inputs got and how often the two reference solutions agreed, and says so.
  • A counterexample is a fact, because your program and both references were run on it. The explanation beside it is not.
  • The benchmark below marks its own homework: the bugs were written by the same agent that built Refute, not collected from real submissions.
  • Refute runs code it did not write. The guard and the sandbox catch mistakes, not attacks, so use the Dockerfile with --network none for anything you do not trust.
  • For practice, not for live contests.
